# Execution Plan: RenderCV Web Editor (rendercv.com clone)

Date: 2026-08-26

## Status

Active

## Outcome

A web application on top of this repository's Python core that reproduces the
rendercv.com editing experience: a three-pane editor (CV list sidebar, editor
pane, live PDF preview) where a CV is edited through four tabs — **CV, Design,
Locale, Settings** — each editable in two synchronized modes (**form editor ↔
raw YAML**), with a theme quick-switcher, live preview, undo/redo, autosave,
and PDF download rendered by the existing `rendercv` pipeline.

## Context

Product reference — observed live on rendercv.com (2026-08-26, logged-in
session) and from the landing-page capture:

- **Stack of the original**: SvelteKit (confirmed by `data-sveltekit-preload-data`,
  Sentry client `sentry.javascript.sveltekit`, `_app/remote/*` remote functions).
- **Rendering is client-side**: the preview PDF comes from a `blob:` URL
  produced by `typst_ts_web_compiler_bg.wasm` (typst.ts). Editing a field
  triggers NO render API call — only `POST /api/files` (debounced autosave)
  and `POST _app/remote/*/savePreferences` (UI state). Telemetry via
  PostHog-style `t.rendercv.com`; errors via Sentry.
- **Editor UX**: 4 tabs map 1:1 to the YAML documents (`cv:`, `design:`,
  `locale:`, `settings:`). A YAML toggle switches raw CodeMirror-style editor
  (line numbers, syntax colors) ↔ schema-driven form (labeled rows,
  placeholders as examples, `+ Add` for arrays, segmented controls for enums,
  toggles for booleans, color swatches, `<` `>` steppers for font/theme
  cycling). Theme switch immediately re-renders preview and swaps
  theme-dependent defaults in the form (e.g. margins 0.7in → 0.6in).
- **Chrome**: undo/redo stack, B/I/link markdown toolbar, zoom controls,
  download/share/link buttons, collapsible sidebar, dark/light toggle,
  AI assistant docked at the bottom (model picker, image attach).
- **Landing page**: dark hero, 5 feature bullets, fanned-out template
  showcase, testimonial marquee, pricing card, FAQ accordion, OAuth CTA.

Repository truth this builds on:

- Core pipeline: YAML → ruamel.yaml → pydantic (`schema/models/`) →
  Jinja2 → Typst → PDF (`renderer/`). See `graphify-out/` for the map.
- `schema.json` (JSON Schema Draft-07, regenerated by `just update-schema`)
  already describes every field — the form editor must be **generated from
  this schema**, not hand-coded per field.
- Validation errors are already user-friendly structured data
  (`RenderCVUserValidationError` + `error_dictionary.yaml`) with YAML
  line/column locations — surface them inline in both editor modes.
- Typst sources for all 9 themes live in
  `src/rendercv/renderer/templater/templates/typst/` and compile with the
  bundled `rendercv_typst` package + `typst_fontawesome` submodule.

## Scope

In scope:

- Monorepo extension: `web/backend` (FastAPI, reuses `rendercv` core) and
  `web/frontend` (SvelteKit + TypeScript + Tailwind).
- The four-tab editor with form ↔ YAML two-way sync and validation.
- Live PDF preview (server-rendered first, typst.ts WASM as an upgrade).
- Theme switcher across the 9 built-in themes.
- Persistence: multi-CV per user, autosave, undo/redo.
- Auth (email magic link or OAuth), PDF download.

Out of scope (later phases, tracked but not planned in detail):

- Payments/pricing, AI assistant, PDF import, GitHub sync, public share
  links, job search.

## Approach

Phased; each phase ends with a working, demoable slice.

**Phase 0 — Scaffold** (backend-engineer + frontend-engineer)
`web/backend`: FastAPI app exposing the core as a service:
`POST /api/validate` (YAML → structured errors), `POST /api/render`
(YAML → PDF bytes), `GET /api/schema` (serve `schema.json`),
`GET /api/themes` (theme list + per-theme design defaults).
`web/frontend`: SvelteKit skeleton with the three-pane layout.

**Phase 1 — YAML-first MVP** (frontend-engineer)
CodeMirror YAML editor for the 4 documents (tabs), debounced (~800ms)
`/api/render` → `blob:` URL into an embedded PDF viewer, inline validation
errors at their YAML line. This is the smallest end-to-end product.

**Phase 2 — Schema-driven form editor** (frontend-engineer + product-analyst)
Generate form components from `/api/schema`: text rows with placeholder
examples, `+ Add`/remove/reorder for arrays (sections, entries, highlights),
enum segmented controls, boolean toggles, color pickers, unit steppers.
Two-way sync: one store holds the parsed document; form and YAML are two
views (YAML comments/key order preserved via ruamel round-trip on the
backend, or a CST-preserving YAML lib on the client).

**Phase 3 — Theme switcher + design/locale/settings forms**
`<` `>` cycler + dropdown; on switch, merge the new theme's defaults into
the design document the way rendercv.com does.

**Phase 4 — Accounts and persistence** (database-architect + backend-engineer)
SQLite → Postgres. Tables: `users`, `cvs` (id, user_id, name, four YAML
documents as text, updated_at), `cv_versions` (autosave snapshots for
undo history across sessions), `preferences`. Debounced autosave endpoint
mirroring `POST /api/files`.

**Phase 5 — Polish and parity**
Client-side typst.ts preview (reuse our own `.typ` templates + fonts in the
browser; server render stays canonical for downloads), undo/redo stack,
markdown toolbar, zoom, dark mode, collapsible sidebar, landing page.

Team operation: use the sub-agents in `.claude/agents/` and skills in
`.claude/skills/` (see `docs/decisions/` when conventions get promoted).
All work on branch `quan`, PRs into `develop`, guardrails hook enforced.

## Risks And Recovery

- **Preview parity** (client WASM vs server PDF): keep server render
  canonical; treat typst.ts as progressive enhancement. Rollback = hide the
  WASM path behind a flag.
- **Form ↔ YAML fidelity** (comments, ordering, anchors): route round-trips
  through ruamel on the backend first; only move parsing client-side when a
  comment-preserving JS YAML layer is proven by tests.
- **Typst compile latency on server**: cache compiled artifacts per
  (yaml-hash, theme); debounce on the client; queue renders per session.
- **Core drift**: the web layer imports `rendercv` as a library — any core
  change runs the existing `just check` + `just test` gates.

## Decisions

- 2026-08-26: Frontend is SvelteKit (matches the observed original; smallest
  path to the same UX). Backend is FastAPI reusing this repo's core rather
  than reimplementing rendering in JS — the Python pipeline is the asset we
  own and test.
- 2026-08-26: Preview starts server-rendered (simple, correct), moves to
  typst.ts WASM in Phase 5 for keystroke-speed feedback. rendercv.com ships
  WASM-only; we keep the server path as the canonical renderer.
- 2026-08-26: Form editor must be generated from `schema.json` — hand-coding
  fields would drift from the pydantic models the moment the core changes.

## Validation

- Focused proof: backend contract tests per endpoint (validate/render/schema/
  themes) using existing test fixtures (`minimal_rendercv_model`, sample
  YAMLs); frontend component tests for form↔YAML sync round-trips.
- Integration or end-to-end proof: Playwright — type in YAML tab, preview
  updates; edit a form field, YAML reflects it; switch theme, defaults merge;
  reload, autosaved state returns.
- Repository-required checks: `just check` and `just test` stay green; web
  workspace adds its own lint/typecheck/test commands to the justfile.
